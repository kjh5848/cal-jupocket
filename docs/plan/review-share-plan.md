# 후기·공유·블로그 기획서 (전세 도우미)

2026-11-22 · PM. 성장 조사(`review-share-growth.md`)와 콘텐츠 조사(`review-share-blog.md`)를 하나로 묶었다. 코드는 고치지 않았다.

## 1. 한 줄 요약과 권고

**작게 한다.** 사용자가 말한 세 가지 중 둘은 지금 시작하고(공유, 블로그), 하나는 "공개"만 문턱을 두고 미룬다(후기).

- 공유: 일을 끝낸 직후 "도움 됐어요/아쉬워요"와 "같이 계약하는 사람에게 보내기"를 도우미 화면 안에 붙인다. 버튼 횟수만 센다.
- 블로그: 새 블로그가 아니라 `/guide/` 전세 글 묶음. 첫 글은 특약 1편, 반응을 본 뒤 갱신거절 날짜·보증금 안 돌려줄 때를 잇는다.
- 공개 후기·별점·자유 글: 지금은 안 한다. 3절에 이유와 여는 문턱을 적었다.

## 3. 문제와 목표, 그리고 "공개 후기" 차이

**문제:** 전세 계약하는 사람이 날짜를 놓쳐 돈을 잃는데, 도우미를 쓴 뒤 "쓸 만했는지"를 우리가 모르고, 쓴 사람이 같이 계약하는 사람에게 넘길 길도 없다.
**목표:** 4주 안에 (1) 어떤 답이 약한지 알고 (2) 공유가 실제로 일어나는지 보고 (3) 검색·AI가 읽을 전세 글을 늘린다.

### 사용자의 말과 전문가 권고의 차이

사용자는 "후기를 남기고 리뷰 남길 수 있게" 하고 "공유할 수 있는 블로그"를 원한다. 두 전문가는 공개 후기를 보류하자고 한다. 이 기획서도 같은 결론이다. 이유는 다음과 같다.

1. **보여 줄 사람이 없다.** 하루 0~몇 명이면 공개 후기는 빈 벽이거나 한두 줄이다. 빈 벽은 신뢰를 깎는다. 운영자가 채우면 표시광고 문제가 되므로 채울 수 없다.
2. **받는 순간 새 개인정보다.** 지금 처리방침은 질문 문장·날짜·페이지만 약속한다. 자유 글은 항목·목적·보유기간을 새로 적어야 한다.
3. **공개하면 운영자 책임이 생긴다.** 광고가 있는 페이지에 사용자 글을 내면 AdSense UGC 정책 대상이다. 정보통신망법상 임시조치 대응 가능성도 있다(조문 미확인, 5절).
4. **운영자가 한 명이다.** 승인·신고 대응을 맡을 사람이 없다.

"좋았다면 후기를 남긴다"는 뜻 자체는 버튼 한 번(도움 됐어요)으로 들어준다. 그러면 사용자의 의도(좋았을 때 표현할 길)는 살고, 위험은 새로 안 생긴다.

### 공개 후기를 여는 문턱

두 조사의 문턱이 다르다. 아래에서 하나로 정한다. **모든 숫자는 근거 있는 값이 아니라 제안값이다.**

| 조사 | 비공개 한 줄 후기를 여는 조건 | 공개를 여는 조건 |
|---|---|---|
| 성장 | `hug_feedback` 응답 20건 | 공개 동의 승인 글 5건 + 법 원문 확인 |
| 콘텐츠 | (처음부터 한 줄 선택 입력 포함) | 승인 항목 약 10건 |

**이 기획서의 문턱(차이를 이렇게 푼다):**
- 1단계 비공개 한 줄 후기: 2주간 `hug_feedback` 응답 20건 이상. 한 줄 입력은 MVP에서 뺀다(콘텐츠 조사는 넣자고 했으나, 넣으면 처리방침 변경과 개인정보 거름 작업이 같이 와서 1~2일을 넘긴다).
- 2단계 공개: 비공개 글 중 쓴 사람이 "공개해도 돼요"를 체크하고 운영자가 승인 기준으로 거른 글이 **10건**(둘 중 더 보수적인 값) 이상, 그리고 5절 법 원문 확인을 마친 뒤.
- 공개 최소 형태: 광고 없는 도우미 화면 안에서만, 승인 글만, 고정 승인 기준(결과 보장·HUG 오인·업체 홍보·욕설·개인정보 제외), 별점·평균·"N명" 숫자 없음, 보상 없음, 삭제 요청 길 있음. 홈·가이드(광고 페이지)에는 내지 않는다.

## 4. 안 비교

| | A. 누르기 + 공유 + 글 1편 | B. A + 비공개 한 줄 후기 + 글 3편 | C. 공개 후기 벽 |
|---|---|---|---|
| 만드는 품 | 1.5~2일 (도우미 0.5~1일 + 글 1편) | 약 4~5일 | 2~3일 + 검수 |
| 처리방침 | 변경 없음 | 변경 필요 | 변경 + 공개 동의·삭제 절차 |
| 운영 부담 | 주 1회 숫자 확인 | 주 1회 승인 대기열 | 신고·임시조치 대응 |
| 기대 | 숫자로 약속 못 함. "어느 답이 약한가", "공유가 일어나나" 신호 | 말투 담긴 문장, 글 소재 | 사용자가 적어 빈약해 보임 |
| 위험 | 낮음 | 개인정보 섞임 | 법·UGC 쟁점 전부 |
| 판정 | **권장** | 문턱 통과 후 | 지금 안 함 |

### 둘 다 "확인 못 함"으로 남긴 것

법 원문 (`law.go.kr` 본문이 열리지 않았고 2차 보도·일반 지식에 기댔다):
- 표시광고 추천·보증 심사지침(공정위예규 제499호) 후기 조항, 사업자가 후기를 고르거나 지우는 행위 규정
- 개인정보 보호법 제2조·제3조·제15조·제30조 (한 줄 후기를 받을 때 처리방침 기재)
- 정보통신망법 제44조·제44조의2 (공개 후기의 운영자 책임)
- AdSense UGC 정책 중 "게시자 콘텐츠 없는 화면", 관리 권장안의 정확한 문구
- GA4·Clarity 가 URL 해시를 수집하는지

검색·유입:
- 전세 키워드 월 검색량·SERP. 글 3편의 "더하는 것"과 유입 기대는 가설이다.
- GA4 숫자 일체는 저장소에서 재확인하지 못했다.
- Cloudflare 관리형 블록에서 OAI-SearchBot·PerplexityBot·Claude-SearchBot 허용 여부, 네이버 Yeti·서치어드바이저 RSS 제출 여부
- 도우미 전용 OG 이미지 존재, 도우미가 `?q=` 로 특정 질문을 여는지(못 찾음), `InstallApp` 이 언제 뜨는지

## 6. 권하는 MVP (1~2일)

### 화면과 흐름
1. **일을 끝낸 직후 한 줄.** 캘린더 내려받기나 알림을 켠 직후 같은 말풍선 아래에 "도움이 됐어요 / 아쉬워요"와 "같이 계약하는 사람에게 보내기". 모달·팝업 없음. 한 번 답하거나 "나중에"를 누르면 `localStorage` 에 남겨 다시 묻지 않는다.
2. **"아쉬워요" 뒤 이유 칩** (날짜가 달라요 / 내 상황이 없어요 / 너무 어려워요 / 틀린 것 같아요 / 기타). 글은 못 쓴다.
3. **AI 답 아래 작은 엄지(위·아래).** 답 품질 신호.
4. **보내기** 두 갈래. ① 도구 소개: 고정 링크 `https://jupocket.com/jeonse-chat/?s=contract&utm_source=share&utm_medium=native` 와 한 줄 문장, 날짜 없음. ② 내 일정 보내기: 사용자가 누를 때만 브라우저에서 텍스트·이미지(`result-card.ts` 재사용)를 만들고, 날짜 포함이 기본, "날짜 빼고 보내기"를 같은 자리에 둔다. 이미지 맨 아래에 "JU포켓이 계산한 날짜, HUG 일정이 아니니 HUG·은행에 확인" 고지. 서버를 거치지 않는다.
5. **글 1편: "전세 계약서 특약은 뭐라고 쓰나요"** (`/guide/` 아래). 표준계약서에 인쇄된 문구와 HUG 안내를 출처·확인일 포함해 분리, 숫자는 `rates` 템플릿, `hug-answers` 문장 복붙 금지, 글 끝에 도우미 입구, OG 이미지 만들기.

### 저장 데이터
- 서버: 새 표 없음. `hug_feedback`(키 `plan_up`·`plan_down`·`answer_up`·`answer_down`), `hug_feedback_why`(`date`·`case`·`hard`·`wrong`·`other`), `hug_share`(`native`·`copy`·`image`·`text`·`nodate`) 를 `track()` 으로 보낸다. 이름·키 규칙(`^hug_[a-z_]{1,30}$`)을 이미 만족하며 `/admin/` 에서 보인다.
- 기기: 답했는지 여부만 `localStorage`.

### 개인정보 처리방침
변경 없음. 버튼 횟수만 센다는 기존 문장 범위 안이다. 공유 텍스트·이미지는 사용자 기기에서 만들어져 서버를 거치지 않으므로 "일정은 이 브라우저에만 저장" 문장과 충돌하지 않는다. 한 줄 후기를 받는 날은 같은 배포에서 `privacy.astro` 전세 도우미 절을 고친다(3절 1단계).

### 하지 않는 것과 이유
별점(사용자 적어 평균이 의미 없음), 자유 글·한 줄 후기(개인정보·처리방침), 공개 후기 칸(3절), 후기 숫자·"후기 0개" 문구(없는 것을 드러내지 않음), 보상, 카카오 SDK 버튼(`navigator.share` 로 카톡이 뜸), 허브 페이지와 네이버 블로그(스포크 3~4편 뒤), 글 끝 "도움이 됐나요"(이벤트 가능 여부 확인 뒤).

## 7. 시작 전 점검 (품 한 시간 이내)
1. 공유받은 사람이 `?s=contract` 로 들어와 날짜 칸에 한 번에 닿는지, 일정 질문이 2개로 줄었는지 확인한다. 안 되면 공유는 새는 물이다. 지금 구현 중인 변경이 이 조건이다.
2. Cloudflare 에서 검색용 AI 봇(OAI-SearchBot·PerplexityBot·Claude-SearchBot) 차단 여부 확인.
3. 글 쓰기 전 시드 키워드(전세 특약, 갱신거절 통보, 임차권등기, 공시송달 전세, 보증 거절)로 SERP 를 한 번 훑는다.
4. 도우미 전용 OG 이미지(1200x630) 존재 확인.

| 응답 수 | `hug_feedback` 합계 | 20건 이상이면 3절 1단계 검토 | 2주, 4주 |
| 공유 발생 | `hug_share` 합계, GA4 `utm_source=share` 유입 | 4주 안에 1건이라도 있으면 신호. 0이면 공유 기능이 안 쓰인 것 | 4주 |
| 공유받은 사람 | `utm_source=share` → `hug_chat_stage contract` → `hug_plan_done` | 비율만 본다 (표본 작아 단정 안 함) | 4주 |
| 약한 답 | `answer_down` 많은 답, 아쉬워요 이유 분포 | 이유 1위가 `wrong`·`date` 면 그 답을 먼저 고친다 | 매주 월요일 대화 로그 분석과 함께 |
| 새 글 | Search Console 새 URL 노출·클릭, GA4 AI 출처 세션 | 4주에 노출 0이면 "전세 롱폼에 검색 의도가 있다"는 가설부터 의심 | 4주 |

접는 선: 4주 동안 응답 20건 미만이고 공유 0이면 후기·공유 기능은 더 키우지 않고 말풍선 버튼만 남겨 둔다. 그리고 문제는 후기가 아니라 유입이라고 보고 글 쪽(새 글 3편)과 유입 쪽으로 힘을 옮긴다. 4주에 새 글 노출이 0이면 전세 글 확장도 멈춘다.

## 9. 위험과 막는 방법

| 위험 | 막는 방법 |
|---|---|
| 숫자 부풀림(같은 사람이 여러 번 누름) | 기기당 1회(`localStorage`), 숫자는 참고로만. 30건 미만이면 공개 안 함(제안값) |
| 공유로 날짜·금액이 새어 나감 | 링크는 고정 문자열, 날짜를 쿼리·해시에 싣지 않음, 내 일정 보내기는 사용자 클릭 때만, "날짜 빼고" 선택 |
| 지어낸 후기·가상 사례 | 가짜 후기·표시 없는 가상 사례 금지. 글의 사례는 "가상 사례"를 맨 위에 적고 결과는 사이트 계산 코드 값 |
| "사용자가 실제로 물은"이라고 쓴 글 | 58개는 예상 질문이다. 로그 기반 글은 로그가 쌓인 뒤 표본 수와 함께만 |
| 법률 자문처럼 읽힘, 숫자 오류 | 비공식·법률 자문 아님 고지, 숫자는 `rates` 템플릿, 출처·확인일 표기, 법률구조공단 안내 |
| 보상 후기 미표시 쟁점 | 보상 없음(쿠폰·경품·우선 안내 모두) |
| 글 속 실명 사기 이야기 | 유튜브 사례는 유형으로만, 영상 속 숫자는 쓰지 않음 |
| 새 평가 UI 가 다른 팝업과 겹침 | `InstallApp` 이 도우미에서 언제 뜨는지 먼저 확인 |

## 11. 사용자가 정해야 할 것

1. **"공유할 수 있는 블로그"는 어느 쪽을 뜻했나요?**
   - (권장) 전세 안내 글을 계속 써서 공유하기 좋게 만든다 (`/guide/` 글 묶음, 첫 글은 특약)
